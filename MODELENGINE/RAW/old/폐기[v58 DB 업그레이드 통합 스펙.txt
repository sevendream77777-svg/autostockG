2) 전처리·단위·품질 규정(정합성·레이턴시·결측)
- 단위: 금액 KRW, 금리 %, 수급 qty=주/amt=KRW.
모든 소스에서 단위가 다를 경우 수집 단계에서 표준화.
- 타임존/캘린더: Asia/Seoul, KRX 영업일 캘린더 고정. 휴장/정지일 마스크.
- 결측: 원천 레벨 NaN 보존(특히 수급). 피처 단계에서만 정책 적용(유형별 median/IQR 대체 혹은 0 허용 목록).
- 이상치: winsorize(1~99%) 또는 robust scaler(세트별 고정) 적용.
- 레이턴시 표(SLA): 가격·수급 T+0, 재무/일부 매크로 T+1 허용. SLA 문서(source_sla.yaml)에 수집시각/허용지연/재시도/백오프 명문화.

3) PIT 설계(누수 방지 핵심)
- 원칙: “row.date 시점에서 미래 정보 접근 금지”
- 재무/섹터/테마/이벤트는 발표일/유효기간 기반 PIT 테이블로 관리.
- PIT 조인 예시: left join on (code) + 조건(effective_from ≤ date ≤ effective_to).
- 리스트형(theme_list)은 스테이징에서 분해 후 (code, theme_code, effective_from/to) 행 분리 적재.
- 이벤트: 선언일로 조인, 효력발생일 기반 지표는 후행 피처에서만 사용.

4) MASTER TABLE 규격
- 표준 필드명으로 통합된 단일 파케이(또는 연·월 파티션). 
- 파티션: date, row-group: code 정렬 권장.
- shares_outstanding_pit, code_mapping(변경/합병/상폐) 별도 테이블 유지.
- QC: 결측률/분포(PSI/KL)/상관구조/시총 검증 결과를 메타에 기록.

5) 스냅샷(H5) 설계·운영(SOP)
- 목적: 학습/예측 고속 접근을 위한 code×date×feature float32 매트릭스.
- 샤딩: 날짜 단위(YYYY/MM/DD.h5) 또는 피처군 단위(core_120.h5 등).
- 증분 절차: append → temp.h5 → hash/행열/Null 검증 → atomic replace.
- 재압축: 주간/월간 정책 운영.
- 메타: feature_set_version(Core120/Wide300/XL600), feature_hash, calendar_version, source_sla_version 기록.

6) 자동 피처 엔진 — Core120 / Wide300 / XL600
(윈도우 집합 S={5,10,20,60,120}, VOLW={10,20,60}, MA_family={MA,EMA,WMA,TEMA})

6.1 가격
- 수익률: pct_ret_n, log_ret_n (n∈S)
- 변동성: vol_n(std(log_ret_1), n∈VOLW), ATR_14, TR
- 밴드: Bollinger(mid=MA_20, up=mid+2σ), Keltner(EMA_20±k·ATR), 밴드 위치/폭
- 정규화: z_n = (x−MA_n)/std_n

6.2 수급
- cum_flow_(5, 20, 60, 120), flow_z_20, short_pressure=short_sell_qty/volume
- loan_ratio = loan_balance_qty / shares_outstanding_pit

6.3 재무
- 성장률: QoQ/YoY(4Q 시프트), quality_z(by industry, 8Q rolling)
- 가치: value_factor = z(−PER)+z(BPS)+z(ROE) (가중 규칙 문서화)
- 현금흐름: (cash_flow_op − capex)/revenue (capex≈−cash_flow_inv)

6.4 섹터/시장/거시
- sector_ret_n, sector_MA_n, sector_RS = stock_ret_n − sector_ret_n
- market_RS = stock_ret_n − kospi_ret_n
- macro_z(usdkrw,dxy,vix 등, n∈(20, 60)), 


6.5 이벤트(선언일 기준 계산)
- days_to_earnings/ex_div, surprise_scaled(winsorized)
- event_past_flag_k: (date − announce_date ≤ k), k∈(5, 10, 20)

6.6 세트별 정책
- Core120: 저변동·저상관 중심 안정형(≈120개)
- Wide300: 윈도우·가족(EMA/WMA/TEMA) 확장, RS/수급 확대(≈300개)
- XL600: 교차항 추가(price_z20×flow_norm, sector_RS×macro_z 등).
정규화된 변수끼리만 교차. 상관상한 |ρ|≤0.95 후 600±5로 고정.

## 1.1 전체 파이프라인의 구조적 일관성
v58 구조는 다음 7단이 완전하게 연결되는 형태:
1) RAW 수집 계층  
2) STAGING(정합성/단위/형식 정규화)  
3) PIT(발표일 기반 실적, 이벤트, 주식수, 권리 데이터)  
4) MASTER(거래/수급/재무/섹터 통합)  
5) H5(엔진 입력 스냅샷)  
6) FEATURE(120/300/600 계층)  
7) ENGINE(모델 학습/서빙)

이러한 계층식 구조는 확장성과 재현성을 동시에 보장한다.
데이터 계보(lineage)의 연결이 분명하기 때문에 장애 원인 추적과 디버깅이 용이하다.
## 1.2 PIT(발표일 기반) 구조의 우월성
한국 시장 데이터 특성상:
- 재무공시 시차가 일정하지 않음
- 이벤트(분할·합병·유상증자 등)가 ‘효력일’과 별개인 ‘선언일’을 가짐
따라서 발표일 기반 PIT 구조는 누수(leakage)를 원천 차단한다.
특히 재무 데이터는:
- effective_from = 공시 발표일
- effective_to = 다음 공시 전일
구간으로 정의하는 것이 이상적 구조이며
v58 구조가 이를 명확히 지원한다.
## 1.3 Feature 계층화 (Core120 / Wide300 / XL600)
3중 피처 계층은 다음 장점이 있다.
- Core120: 안정성, 데이터 품질, 전 종목 커버리지 확보
- Wide300: 유의미한 기술지표 + 수급지표 + 매크로 확장
- XL600: 실험적/연구용 포함, 모델 다양성(ensemble) 극대화

계층별로 유지됨으로써 엔진 간 비교와 교차 검증이 쉽고,
장기적으로 SLE/HOJ 혼합 모델에도 유리하다.
## 1.4 이벤트 기반 학습의 탁월함
한국 시장은 분할/액면변경/배당락/권리락 등 이벤트가 많아
이벤트 기반 리턴 정의를 명확히 하는 것이 필수다.
v58 스펙의 장점은 다음과 같다:
- 분할/병합 이벤트가 adj_factor와 조정가격에 정확히 반영
- 배당락은 조정가 기반 리턴 사용으로 누적 수익률 왜곡 제거
- 증자/감자와 PIT ‘주식수 변동’의 시계열 정렬이 명확


## 1.5 엔진 메타 구조의 표준화
각 엔진은 다음과 같은 메타를 가진다:
- engine_version
- last_data_date
- last_train_date
- feature_set 정보
- 조정가/비조정가 기준
- 실제 사용된 피처 리스트 hash

이 메타는 엔진 검증/서빙 안정성의 핵이다.

-----------------------------------------------------

### 원인
한국 시장은 분할/병합 이벤트가 많아 단순값만 쓰면 리턴이 왜곡된다.

### 적용 규칙

## 7.1 실행 모드 분리 (Cold Start vs Incremental)
### 문제
단순히 파일 유무로 로직을 자동 분기하면, 피처 로직 변경 시 과거/현재 데이터가 섞이거나 스키마 불일치로 인한 DB 오염이 발생함.
### 해결: 실행 인자(Argument)를 통한 모드 명시적 분리
1. **`--mode daily` (기본 운영)**
   - 동작: 기존 H5/Parquet 파일 로드 → 마지막 날짜(last_date) 확인 → 그 이후 데이터만 계산 → Append.
- 필수 체크: 기존 파일과 신규 데이터의 컬럼 개수/순서/이름 일치 여부 (Assertion). 불일치 시 에러 발생 및 중단.
2. **`--mode full` (초기 구축/로직 변경/재생성)**
   - 동작: 기존 파일 백업(또는 삭제) → 전체 기간(예: 10년) 벡터 연산(Vectorized)으로 일괄 생성.
- 특징: 루프 방식이 아닌 행렬 연산을 사용하여 대량 데이터 생성 속도 최적화. 스키마 변경 시 필수 사용.
## 7.2 윈도우 환경 파일 잠금(Locking) 방지 대책
### 문제
리눅스와 달리 Windows 환경에서는 파일이 열려있거나(UI/Jupyter 등) 존재할 경우 `os.rename`이 원자적(Atomic)으로 동작하지 않아 `PermissionError` 발생 및 데이터 유실 위험.
### 해결: 안전한 파일 교체 루틴 구현
1. 임시 파일 생성: 작업은 반드시 `temp_filename.h5`에서 수행.
2. 교체 로직:
   - Step 1: `if os.path.exists(target): os.remove(target)` (단, Retry 로직 포함).
- Step 2: `shutil.move(temp, target)` 또는 `os.rename(temp, target)`.
   - Step 3: 실패 시 `temp` 파일 유지 및 에러 로그 기록 (데이터 유실 방지).
## 7.3 스토리지 용량 관리 (Retention Policy)
### 문제
일별 스냅샷(H5)과 엔진(pkl), 알림 이미지(png)가 무제한 누적되어 디스크 Full 장애 유발.
### 규칙 (자동 삭제 정책)
1. **H5 스냅샷:** 최신 **5개 버전(일자)**만 유지, 오래된 파일 자동 삭제.
2. **JSON/이미지:** 생성 후 **30일** 경과한 파일 자동 삭제.
3. **로그(Log):** 7일 보관 후 회전(Rotate) 또는 삭제.
4. 구현 위치: `main.py` 종료 직전 `clean_up()` 함수 호출.
